# profile-site 기획

작성 시작: 2026-07-29

내용(이름, 소개, 링크 목록)과 디자인은 **아직 정하지 않는다.**
이 문서는 그 앞 단계 — **무엇을 어떤 도구로 어디에 띄울지**를 정한다.

---

## 1. 1차 목표

> **`https://elkiss.me` 를 열면 "Hello World" 가 뜬다.**

이게 전부다. 예쁠 필요 없고, 내용이 있을 필요도 없다.
목적은 **파이프라인 검증**이다 — 도메인, DNS, GitHub Pages, HTTPS 인증서까지
네 개가 연결되는 걸 한 번 끝까지 해보는 것.

이게 되고 나면 그 다음부터는 HTML 파일만 고치면 되고, 인프라는 다시 안 건드린다.

**완료 조건**

- [ ] `elkiss.me` 도메인 소유
- [ ] DNS 레코드가 GitHub Pages를 가리킴
- [ ] `https://elkiss.me` 접속 시 페이지가 뜸
- [ ] 자물쇠 아이콘 정상 (HTTPS, 인증서 경고 없음)
- [ ] `http://` 로 들어가도 `https://` 로 자동 전환됨

## 2. 도메인

### 2.1 목표 도메인

`elkiss.me`

2026-07-29 기준 DNS 조회 시 `NXDOMAIN` (존재하지 않음) → **미등록 가능성이 높다.**
단, DNS 조회는 확정 근거가 아니다. 등록만 해두고 네임서버를 안 붙인 도메인도
똑같이 안 잡힌다. **레지스트라 검색창에서 실제 확인이 필요하다.**

### 2.2 .me 가 뭔지

몬테네그로 국가 도메인(ccTLD)인데, 등록 제한이 없고 영어로 "나"를 뜻해서
개인 프로필 사이트에 관행적으로 많이 쓴다. 국적·거주지 요건 없음.

주의할 점 하나: **.me 는 .com 보다 갱신비가 비싸다.** 연 $15~20 선.
첫해 $2 짜리 미끼 가격을 내걸고 2년차에 $30 을 받는 곳이 많으니
**첫해 가격이 아니라 갱신 가격을 보고 골라야 한다.**

### 2.3 어디서 살까

| 레지스트라 | 등록(1년) | 갱신(연) | 메모 |
|---|---|---|---|
| **Cloudflare Registrar** | $16.56 | $16.56 | 원가 판매, 마크업 0. 첫해 할인 없음 = 미끼도 없음. DNS 같이 제공 |
| Porkbun | 저가 | 등록가와 동일 | 첫해/갱신 가격 같음. WHOIS 프라이버시 무료 |
| Dynadot | $9.56 | $17.53 | 첫해 싸고 갱신에서 회수 |
| Namecheap | 할인 | 인상됨 | 첫해 할인 후 갱신가 상승 구조 |
| GoDaddy 류 | 매우 쌈 | 매우 비쌈 | 업셀 많음. **비추천** |

> 가격은 2026년 중반 조사 기준. 살 때 다시 확인할 것.

**추천: Cloudflare Registrar**

이유가 셋이다.

1. **원가 판매** — 첫해/갱신 가격이 같아서 몇 년 뒤 청구서에 놀랄 일이 없다.
2. **DNS가 같이 온다** — 도메인 산 곳과 DNS 관리하는 곳이 같으면 설정이 한 화면에서 끝난다.
3. **apex 도메인에 CNAME 을 걸 수 있다** — 아래 2.4 에서 설명. 이게 실질적으로 제일 크다.

단점: 무료 Cloudflare 계정 가입이 필요하고, DNS를 반드시 Cloudflare 걸 써야 한다.
지금 상황에선 둘 다 문제가 안 된다.

Porkbun 도 충분히 좋은 선택이다. UI가 더 단순하다.

### 2.4 apex 도메인 문제 (알아둘 것)

`elkiss.me` 처럼 앞에 아무것도 안 붙은 걸 **apex(루트) 도메인**이라고 한다.
`blog.elkiss.me` 는 서브도메인.

DNS 표준상 **apex 에는 CNAME 을 걸 수 없다.** 그래서 GitHub Pages에 연결하려면
원래는 IP 주소를 A 레코드에 직접 적어야 한다 — GitHub이 IP를 바꾸면 사이트가 죽는다.

Cloudflare(그리고 일부 DNS 제공자)는 **CNAME flattening / ALIAS** 라는 걸 지원해서
apex 에도 이름으로 걸 수 있게 해준다. 이러면 GitHub이 IP를 바꿔도 알아서 따라간다.
**이게 Cloudflare를 추천하는 진짜 이유다.**

### 2.5 구매 전 확인

- [ ] 레지스트라 검색창에서 `elkiss.me` 실제 가용 여부 확인
- [ ] 갱신 가격 확인 (첫해 가격 말고)
- [ ] WHOIS 프라이버시 포함인지 확인 — 없으면 집주소/전화번호가 공개된다
- [ ] 자동 갱신 켤 것 — 깜빡하고 만료되면 남이 채간다

> 도메인 구매는 직접 한다. 결제 정보 입력은 Claude가 하지 않는다.

## 3. GitHub Pages 연결 절차

도메인을 산 다음의 순서다. **순서대로 해야 한다.**

### 3.1 GitHub 쪽

1. 저장소 `Settings` → `Pages` → Source 를 `main` 브랜치로 지정
2. 같은 화면 `Custom domain` 에 `elkiss.me` 입력 → Save
   - GitHub이 저장소 루트에 `CNAME` 파일을 자동 커밋한다. 지우면 안 된다.

### 3.2 DNS 쪽

**Cloudflare(또는 ALIAS 지원 DNS)를 쓰는 경우 — 권장**

| Type | Name | Value | Proxy |
|---|---|---|---|
| CNAME | `@` | `elkiss87.github.io` | **DNS only (회색 구름)** |
| CNAME | `www` | `elkiss87.github.io` | DNS only |

**A 레코드로 하는 경우 — ALIAS 미지원 DNS**

`@` 에 A 레코드 4개:

```
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153
```

IPv6도 같이 넣으려면 AAAA 레코드 4개:

```
2606:50c0:8000::153
2606:50c0:8001::153
2606:50c0:8002::153
2606:50c0:8003::153
```

> ⚠️ **Cloudflare 프록시(주황 구름)는 처음엔 반드시 꺼둔다.**
> 켜두면 GitHub이 Let's Encrypt 인증서를 발급받지 못해서 HTTPS가 안 잡힌다.
> 사이트가 정상적으로 뜬 다음에 켜볼지 말지 판단한다.

> ⚠️ 와일드카드 레코드(`*`)는 쓰지 않는다. 도메인 탈취 위험이 있다.

### 3.3 마무리

3. DNS 전파 대기 — **최대 24시간**. 보통은 몇 분~1시간.
4. `Settings` → `Pages` 로 돌아가서 **Enforce HTTPS** 체크
   - 인증서 발급 전이면 체크박스가 회색이다. 기다렸다 다시 온다.
5. 시크릿 창에서 `https://elkiss.me` 접속 확인

### 3.4 나중에: 서브도메인

GitHub Pages는 **저장소 하나당 커스텀 도메인 하나**만 붙는다.
그래서 블로그는 별도 저장소 + 서브도메인으로 간다.

| 용도 | 도메인 | 저장소 |
|---|---|---|
| 프로필 (지금) | `elkiss.me` | `profile-site` |
| 블로그 (나중) | `blog.elkiss.me` | 별도 저장소 |

서브도메인은 apex 문제가 없어서 그냥 CNAME 한 줄이면 된다.

## 4. 기술 스택

### 4.1 먼저 짚을 것 — 여긴 웹 서버를 고르는 자리가 아니다

.NET 하던 감각이랑 가장 크게 다른 지점이다.

**GitHub Pages 는 정적 파일 호스팅이다.** 파일을 올려두면 그대로 내려주는 게 전부다.

- 서버에서 도는 코드가 **없다**. C# 도, PHP 도, Node 도 안 돈다.
- DB 없음, 세션 없음, 로그인 없음, API 없음
- IIS / Kestrel / nginx 중에 뭘 쓸지 **고르지 않는다.** GitHub이 자기네 CDN으로 알아서 서빙한다.

그래서 "웹 서버 뭐 쓰지?"의 답은 **"고를 게 없다"** 이다.
서버가 필요해지는 순간 GitHub Pages를 벗어나야 한다 (그럴 일 없을 것 같다).

### 4.2 그럼 언어는 뭘 쓰나

브라우저가 아는 언어는 **HTML / CSS / JavaScript** 셋뿐이다. 예외 없다.

React, Blazor, Jekyll 같은 건 "다른 언어로 웹을 만드는 도구"가 아니라
**빌드 시점에 HTML/CSS/JS 를 뽑아내는 도구**다.
C#으로 짜든 TypeScript로 짜든, 결국 브라우저에 도착하는 건 HTML/CSS/JS 다.

### 4.3 후보 검토

| 기술 | Pages에서 | 판정 |
|---|---|---|
| **순수 HTML/CSS** | 파일 그대로 올림 | ◎ 빌드 없음, 바로 됨 |
| **Jekyll** | Pages에 내장, 설정 없이 동작 | ○ 블로그용으로 좋음 |
| **Astro / Hugo / 11ty** | Actions로 빌드해서 배포 | ○ 콘텐츠 사이트에 좋음 |
| **React (Vite 빌드)** | 정적 파일로 뽑아 배포 | △ 됨. 링크 페이지엔 과함 |
| **Blazor WebAssembly** | `wwwroot` 를 정적 배포 | △ **된다.** 아래 참고 |
| **MudBlazor** | Blazor WASM 위에서 동작 | △ WASM 되면 됨 |
| **Blazor Server** | SignalR + 상시 실행 .NET 서버 필요 | ❌ 불가 |
| **ASP.NET MVC** | 서버 렌더링 | ❌ 불가 |

**Blazor WASM 에 대해** — 궁금해한 부분이라 따로 적는다.
정말로 GitHub Pages에서 돌아간다. .NET 런타임이 WebAssembly로 브라우저에서 실행되고,
`dotnet publish` 결과물이 정적 파일이라 그대로 올리면 된다. MudBlazor도 같이 쓸 수 있다.
다만 걸리는 게 셋이다.

1. **첫 로딩에 .NET 런타임을 수 MB 받는다.** 모바일 우선 링크 페이지에서 이건 치명적이다.
   방문자가 인스타에서 눌러서 들어오는데 흰 화면이 몇 초 뜬다.
2. SPA 라우팅이 Pages에서 안 맞아서 `404.html` 우회가 필요하다.
3. `<base href>` 를 배포 경로에 맞게 손봐야 한다.

즉 **"할 수 있냐"는 예스, "여기 쓸 거냐"는 노**다.

**MVC 패턴에 대해** — MVC는 서버에서 요청을 받아 뷰를 렌더링하는 패턴이다.
서버가 없으니 해당 사항이 없다. (프론트엔드에도 비슷한 구조가 있지만 다른 얘기다.)

### 4.4 결정

> **1차 목표는 순수 HTML 파일 하나로 간다.** 빌드 도구 없음, 프레임워크 없음.

이유:

1. **1차 목표가 "페이지 만들기"가 아니라 "파이프라인 검증"이다.**
   빌드 단계가 끼면 사이트가 안 떴을 때 DNS 문제인지 빌드 문제인지 배포 문제인지
   구분이 안 된다. 변수를 하나로 줄인다.
2. 링크 페이지는 실제로 HTML/CSS 로 충분하다. 프레임워크가 해결해줄 복잡도가 없다.
3. 나중에 갈아타는 비용이 싸다. 반대 방향(프레임워크 → 순수 HTML)이 훨씬 비싸다.

**프레임워크는 블로그에서 고른다.** 블로그는 어차피 별도 저장소니까
그때 Astro / Jekyll / Blazor WASM 중에 다시 판단하면 된다.
지금 정할 필요가 없고, 지금 정하면 근거 없이 정하게 된다.
