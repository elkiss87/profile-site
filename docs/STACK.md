# 기술 스택

무엇으로 만들지 정한 근거. 결론은 **순수 HTML 파일 하나**다.

---

## 1. 웹 서버를 고르는 자리가 아니다

.NET 감각과 가장 크게 다른 지점이다.

**GitHub Pages는 정적 파일 호스팅이다.** 파일을 올려두면 그대로 내려주는 것이 전부다.

- 서버에서 도는 코드가 **없다**. C#도 PHP도 Node도 돌지 않는다
- DB 없음, 세션 없음, 로그인 없음, API 없음
- IIS / Kestrel / nginx 중에 무엇을 쓸지 **고르지 않는다.** GitHub이 자기네 CDN으로 서빙한다

"웹 서버 뭘 쓰지?"의 답은 **"고를 것이 없다"** 이다.
서버가 필요해지는 순간 GitHub Pages를 벗어나야 한다.

---

## 2. 언어는 셋뿐이다

브라우저가 아는 언어는 **HTML / CSS / JavaScript** 뿐이다. 예외가 없다.

React, Blazor, Jekyll 같은 것은 "다른 언어로 웹을 만드는 도구"가 아니라
**빌드 시점에 HTML/CSS/JS를 생성하는 도구**다.
C#으로 짜든 TypeScript로 짜든 브라우저에 도착하는 것은 HTML/CSS/JS다.

---

## 3. 후보 검토

| 기술 | Pages에서 | 판정 |
|---|---|---|
| **순수 HTML/CSS** | 파일 그대로 업로드 | ◎ 빌드 없음 |
| **Jekyll** | Pages에 내장, 설정 없이 동작 | ○ 블로그용으로 좋음 |
| **Astro / Hugo / 11ty** | Actions로 빌드해서 배포 | ○ 콘텐츠 사이트에 좋음 |
| **React (Vite 빌드)** | 정적 파일로 뽑아 배포 | △ 가능. 링크 페이지엔 과함 |
| **Blazor WebAssembly** | `wwwroot` 를 정적 배포 | △ 가능. 아래 참고 |
| **MudBlazor** | Blazor WASM 위에서 동작 | △ WASM이 되면 가능 |
| **Blazor Server** | SignalR + 상시 실행 .NET 서버 필요 | ❌ 불가 |
| **ASP.NET MVC** | 서버 렌더링 | ❌ 불가 |

### Blazor WASM 에 대해

정말로 GitHub Pages에서 동작한다. .NET 런타임이 WebAssembly로 브라우저에서 실행되고,
`dotnet publish` 결과물이 정적 파일이라 그대로 올리면 된다. MudBlazor도 함께 쓸 수 있다.

다만 걸리는 것이 셋이다.

1. **첫 로딩에 .NET 런타임을 수 MB 받는다.** 모바일 우선 링크 페이지에서 치명적이다.
   방문자가 인스타그램에서 눌러 들어오는데 흰 화면이 몇 초 뜬다.
2. SPA 라우팅이 Pages와 맞지 않아 `404.html` 우회가 필요하다.
3. `<base href>` 를 배포 경로에 맞게 조정해야 한다.

**"할 수 있냐"는 예스, "여기 쓸 거냐"는 노다.**

### MVC 패턴에 대해

MVC는 서버에서 요청을 받아 뷰를 렌더링하는 패턴이다.
서버가 없으니 해당 사항이 없다. (프론트엔드에도 유사한 구조가 있지만 다른 얘기다.)

---

## 4. 결정

> **순수 HTML 파일 하나로 간다.** 빌드 도구 없음, 프레임워크 없음.

이유가 셋이다.

1. **1차 목표가 "페이지 만들기"가 아니라 "파이프라인 검증"이다.**
   빌드 단계가 끼면 사이트가 안 떴을 때 DNS 문제인지 빌드 문제인지 배포 문제인지
   구분이 안 된다. 변수를 하나로 줄인다.
2. 링크 페이지는 실제로 HTML/CSS로 충분하다. 프레임워크가 해결해줄 복잡도가 없다.
3. 나중에 갈아타는 비용이 싸다. 반대 방향(프레임워크 → 순수 HTML)이 훨씬 비싸다.

**프레임워크는 블로그에서 고른다.** 블로그는 별도 저장소이므로
그때 Astro / Jekyll / Blazor WASM 중에 다시 판단하면 된다.
지금 정할 필요가 없고, 지금 정하면 근거 없이 정하게 된다.
